# Hassos MCP ESPHome worker

This companion app runs a pinned ESPHome 2026.10.2 toolchain, independently of ESPHome Builder. It has no Home Assistant configuration mount, Supervisor API permissions, USB devices or Docker socket. The MCP app sends bounded private configuration snapshots over an authenticated, private HTTP connection. Only referenced secrets are forwarded to the worker; they are not returned to ChatGPT.

## HAOS setup

1. Refresh this repository in the add-on store and install **Hassos MCP ESPHome worker**.
2. Generate a dedicated random token, for example `openssl rand -hex 32`. Set `worker_token` in the worker and the matching **ESPHome worker authentication token** in the MCP app. Do not reuse a HA/OpenAI key.
3. Start the worker. Copy its Hostname from Information. Set the MCP app's **ESPHome worker URL** to `http://HOSTNAME:6053`, save and restart the MCP app. No host port is published.
4. Confirm `esphome_validate` returns the installed toolchain version. The worker needs LAN access for device diagnostics and internet access for compiler packages. A `.local` name may not resolve across container networks; set the device's correct `wifi.use_address` in its source configuration through a reviewed change when needed.

For Compose, set `ESPHOME_WORKER_URL=http://esphome-worker:6053` and a dedicated `ESPHOME_WORKER_TOKEN` in `.env.local`, then run `docker compose --env-file .env.local --profile esphome up -d --build`. The worker receives only its own token and uses a private data volume. Its control process has only CHOWN/SETUID/SETGID/KILL capabilities; each toolchain job runs as a distinct unprivileged UID with private files. The container has a read-only filesystem and memory, CPU and process limits. Use HTTPS if connecting across an untrusted network; do not expose the worker to the internet.

## Supported runtime scope

Standalone ESP8266/ESP32 YAML is supported, including native components, substitutions, `!secret` and `!lambda`. Includes, packages, custom components, custom compiler hooks/options and local build inputs are deliberately rejected before toolchain execution. Flatten those configurations locally before using the managed runtime. Source reading remains available for broader configurations. The compiler never gets the live HA configuration directory or HA/tunnel credentials. Runtime operations do not rewrite the original file or restart HA/Builder.

`esphome_get_status` returns separate job `status` and device `availability`. Online requires a fresh native API handshake and device-info response. Failed authentication/name resolution yields unknown; timeout/refusal means the native API is unreachable, not necessarily that power is off. `esphome_get_logs` supports device subscriptions (up to eight seconds, 1–500 lines) and retained build/validation logs. Logs are bounded to 64 KiB and scrubbed against referenced secrets and credential patterns. Arbitrary unlabelled secrets in device messages cannot be recognized reliably; never intentionally log credentials.

`esphome_validate` uses isolated temporary snapshot files. Operations that take more than 20 seconds return `operation_id`; poll `esphome_operation_status` instead of repeating them. Persistent results include version, timestamps, bounded logs and explicit errors. One worker job runs at a time. Restarted jobs become unknown and are never restarted automatically. Worker data contains private snapshots and logs: include it in backups and protect those backups.

## Firmware and OTA

1. Inspect the source and physical wiring. For source edits, validate/propose/review/apply through the MCP config tools; config approval grants no firmware-install permission.
2. Call `esphome_compile(device)`, optionally specifying an applied `approved_config_proposal_id`. Poll `esphome_operation_status` while running. A successful build returns an immutable `artifact_id`, `firmware_sha256`, toolchain version, platform/board, source/snapshot hashes and bounded logs. Compilation never contacts the device or installs anything.
3. Use `esphome_get_status` to inspect live identity, and independently confirm the intended MAC/device. Call `esphome_propose_install(device, artifact_id, firmware_sha256, expected_mac)`. This requires an **encrypted native API** handshake, matching MAC, exact board/model/name, and current source/referenced secrets identical to the build snapshot. It pins the observed private LAN address. Offline/unauthenticated/incompatible devices cannot get an installation proposal. Name/board/API-address changes that prevent matching the current device require an out-of-band recovery workflow.
4. Review the exact firmware hash, identity, address and GPIO/reboot effects; explicitly accept the proposal. Configure ChatGPT to ask every time for **esphome_install**, enable **allow_esphome_install** in MCP and **allow_install** in the worker (Compose: `ALLOW_ESPHOME_INSTALL=true`). Source-write permission is separate. Call `esphome_install` with the exact device, artifact ID/hash, proposal ID and approved digest.
5. Poll the returned `operation_id`. The worker re-hashes the artifact, repeats the encrypted identity check against the pinned IP and uses exactly one native OTA socket/transfer. It does not call ESPHome's retrying CLI upload wrapper or fall back to another transport. Success means the device acknowledged the transfer; verify behavior and GPIO outputs after reboot separately. A lost connection/timeout after transfer starts is **OUTCOME_UNKNOWN**, never automatically retried. `esphome_change_status` shows the consumed approval and its stable operation ID; its approval status is not proof of successful firmware installation.

Native ESPHome OTA is supported; serial, web-server OTA, bootloader/partition changes and automatic firmware rollback are not. Devices lacking encrypted native API identity must be recovered/configured locally before using this OTA flow. The compile/validation runtime rejects custom build hooks, external components and packages; it never runs a caller-provided shell command. `!lambda` is firmware source compiled for the MCU, not executed on the worker.

Limits: one active job globally (therefore no concurrent builds for one device); validation 120 seconds, status/logs 30 seconds, compilation 30 minutes, OTA 3 minutes. Child processes have 2 GiB address-space, 30-minute CPU, 256 MiB per-file, 128-process and 256-file-descriptor limits; compilation uses one compiler process. Compose additionally caps the worker at 3 GiB, two CPUs and 128 processes. No extra host privileges or mounts are required on HAOS; allocate sufficient VM RAM/storage for ESPHome's toolchain. Firmware artifacts are limited to 16 MiB and logs to 64 KiB. Scratch build directories are removed after jobs; compiler packages, private snapshots/artifacts and results persist. At 1,000 retained jobs, new jobs are refused until an operator archives/resets worker data locally. Run only one worker against a data directory.

Reference interfaces: [ESPHome CLI](https://esphome.io/guides/cli/), [pinned native OTA transport](https://github.com/esphome/esphome/blob/2026.10.2/esphome/espota2.py). This app uses that version's native APIs; upgrade the pinned image and adapter together, with tests.

Build jobs cannot read other jobs, the approval database or worker credentials: only the current private snapshot and shared compiler-package cache are accessible among worker data (system runtime libraries remain readable). Retained jobs are reclaimed by the controller before another job starts. This also blocks cross-job file reads through C++ preprocessing. No SYS_ADMIN, host mounts or Docker socket are granted.

Managed lambdas cannot contain preprocessor markers or inline assembly, and local file inputs are rejected. Lambdas are checked again after substitutions and secrets are resolved, before code generation. Ordinary MCU lambda expressions remain supported.
